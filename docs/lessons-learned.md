# Практический опыт и разобранные ошибки

## Снижение CPU: что известно

На Intel 5405U пользователь сравнил исходное приложение (>30% CPU) и Go-сборку
(<9% суммарно). Задержка по его оценке осталась прежней, экран выглядел лучше.
Численный end-to-end benchmark и парные настройки не сохранены. Это полезное
полевое подтверждение, но причинность отдельных оптимизаций не измерена.

В Go-реализации изменился весь путь данных: нативный JPEG камеры можно отправить
напрямую, WIC декодирует в BGRA, D3D масштабирует и обрабатывает вид, UI не обновляет
полноразмерную Tk PhotoImage на каждом poll. Очереди не накапливают кадры.
Следовательно, переносить следует архитектуру и измерения, а не обещание «Go быстрее».

## Ошибка 1: callback на каждый кадр

**Симптом:** сервер работает несколько минут, затем исчезают все окна; обычного
сообщения приложения нет. GUI EXE не сохранял stderr, журнал Windows не показал причину.

**Доказательство:** диагностическая сборка сохранила стек `syscall.compileCallback →
main.monitors → screenRect → captureScreen`; stderr содержал
`fatal error: too many callback functions`.

В `monitors()` на каждый вызов создавалось новое замыкание `syscall.NewCallback`,
захватывающее результат. Функция выполнялась для каждого кадра экрана. Go хранит
регистрации native callbacks до конца процесса; GC не освобождает эти слоты.
Время до аварии зависело от FPS и уже занятых слотов, поэтому «3–4 минуты» не было timer.
Число доступных слотов — деталь runtime, не константа приложения.

**Исправление:** три постоянных callback entry points: монитор, окно, timer панели.
Контексты перечисления находятся в `sync.Map` под непрозрачным ID и удаляются через
defer после синхронного Windows API. Timer находит панель по HWND; Dispose удаляет запись.

**Проверка:** отдельная копия исходного кода снова упала на лимите; новая прошла
8 000 monitor enumerations и 2 000 window enumerations в четырёх workers.
Затем сервер работал более шести минут, три UDP-потока принимались 240 секунд.

**Переносимый вывод:** искать внутри покадрового цикла регистрацию callback,
event handler, native handle и подписки. Heap может выглядеть умеренным, когда
исчерпывается другой ресурс. Стабильный Go heap не доказывает отсутствие утечки.
Основание lifetime callbacks: [документация Go](https://pkg.go.dev/syscall?GOOS=windows#NewCallback).

## Ошибка 2: двойное освобождение PROPVARIANT

Во время проверки нативных аудиоустройств обнаружилось повреждение Windows heap.
У закреплённой версии go-wca `PROPVARIANT.String()` копирует и освобождает LPWSTR.
Дополнительный `PropVariantClear` освобождал ту же память второй раз.

Исправление находится в `endpointName`: после `String` нет повторного освобождения
этого значения. Это контракт конкретной зависимости, а не общее свойство всех
PROPVARIANT wrappers. При замене библиотеки нужно заново проверить ownership в исходнике.
Короткий тест открытия устройства полезен, но для этого пути нет отдельного
детерминированного regression test на повреждение heap — это граница покрытия.

## Ошибка 3: layout между удалением и добавлением вкладок

Аппаратный self-test, быстро переключающий роли, выявил panic в layout Walk:
старый currentIndex ссылался на уже очищенный список pages. Во время построения
новой формы библиотека могла запустить промежуточный layout.

`forms()` теперь сохраняет состояние Suspended, приостанавливает main window,
перестраивает вкладки и восстанавливает suspension через defer. Текущая вкладка
восстанавливается, `building` подавляет программно вызванные обработчики.
Проверка трёх ролей включена в self-test; обычный `go test` не делает полный UI smoke.

## Граница Go / Windows

Адрес в uintptr не поддерживает lifetime Go-объекта. `invoke/com` принимают
явные pointers, используют Pinner на время вызова и KeepAlive после него.
Это исправляет конкретный путь синхронных вызовов; указатель, сохраняемый native API
после возврата, требует другого механизма владения. Произвольный COM interface
нельзя переносить между apartments только потому, что он представлен числом.

Покадровое FFI следует сопровождать схемой ownership, таблицами ABI, отказоустойчивым
освобождением и тестами, а не только успешной компиляцией. Источники:
[Pinner](https://pkg.go.dev/runtime#Pinner),
[инициализация COM по потокам](https://learn.microsoft.com/en-us/windows/win32/learnwin32/initializing-the-com-library).

## Как не исказить этот опыт

- Preview проверен на ограниченном наборе устройств; универсальности по драйверам нет.
- Линейный resampler не является полноценным DSP-конвертером высокого качества.
- UDP bounded queues не дают гарантии real-time и синхронизации A/V.
- Один процесс экономит взаимодействие, но общий fatal error разрушает все его сеансы.
- Retry после обычного возврата worker не перехватывает fatal и не прерывает зависший драйвер.
- «Нулевой звук loopback» при отсутствии воспроизведения сам по себе не доказывает поломку.
- Аппаратный self-test с exit 0 всё равно нужно читать: часть ошибок записывается в JSON.
