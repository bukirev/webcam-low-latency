# UDP media protocol

Источник истины: [protocol.go](../go-version/protocol.go),
[audio.go](../go-version/audio.go), [audio_windows.go](../go-version/audio_windows.go).
Совместимая Python-реализация: [network.py](../network.py), [audio_stream.py](../audio_stream.py).
Формат не содержит version negotiation: magic одновременно идентифицирует тип протокола.

## Подписка и адреса

| Поток | Magic | Control port по умолчанию | SUB, ASCII без newline |
|---|---|---|---|
| Камера | WC30 | 5001 | `WC30 SUB <receive-port>` |
| Экран | WS40 | 5002 | `WS40 SUB <receive-port>` |
| Звук | WA40 | 5003 | `WA40 SUB <receive-port>` |

Приёмник создаёт UDP4 socket на свободном порту и раз в секунду отправляет SUB.
Пустой host означает broadcast `255.255.255.255`; иначе разрешается имя/IP.
После выбора источника ping направляется ему. Подписчик удаляется сервером через
5 секунд отсутствия SUB. Go video sender принимает указанный receive-port от 1 до
65535; audio sender требует, чтобы он совпадал с реальным UDP source port.

Указанный host фильтрует source IP. Выбранный источник определяется IP и Session,
не исходящим UDP-портом: Python может отправлять media отдельным socket.
Если 2 секунды нет данных, receiver допускает новый источник/сеанс. Видео дополнительно
публикует `nil`, очищая окно.

## Сетевой поиск

Отдельный запрос `<magic> FIND <nonce>` отправляется на UDP-порт выбранного
потока. `nonce` — 16 строчных шестнадцатеричных символов. Передатчик отвечает
`<magic> HERE <nonce> <hostname>`. [Реализация](../go-version/discovery.go)
отправляет ограниченное число probes на broadcast-адреса и loopback, собирает
ответы до 550 мс и ограничивает список 64 конечными точками. Поиск камер в OBS
опрашивает UDP 5001 и 5004–5010, а также заданный вручную порт. Для камеры
выбор сохраняет пару IPv4:порт, поэтому один компьютер может передавать несколько
камер. Старые сцены со значением IPv4 продолжают использовать сохранённый порт.
Для экрана и звука поиск ограничен портом из свойств. Запрос FIND не оформляет подписку.
При заблокированном broadcast или старом передатчике укажите IPv4 вручную.

## Заголовок видео: 20 байт

Все многобайтовые поля — **big-endian**. Python: `struct.Struct('!4sQIHH')`.

| Смещение | Размер | Поле | Значение |
|---|---|---|---|
| 0 | 4 | magic | WC30 или WS40 |
| 4 | 8 | session | Случайный uint64 идентификатор sender |
| 12 | 4 | seq | Номер JPEG uint32, с переполнением |
| 16 | 2 | part index | Номер части с нуля |
| 18 | 2 | part count | Общее число частей 1…4096 |
| 20 | ≤1300 | data | Последовательные байты JPEG |

`part count = ceil(len(jpeg)/1300)`. Последняя часть может быть короче.
Максимум JPEG на этом wire path: `4096*1300 = 5 324 800` байт.
Это меньше отдельного внутреннего предела WIC encoder в 6 MiB; JPEG между этими
двумя пределами ещё может быть закодирован, но `fragments` его не отправит.

`fragments` переиспользует один packet buffer. Callback отправки обязан завершить
чтение до возврата либо скопировать срез. Нельзя просто положить его адрес в async queue.

Assembler проверяет размер/magic/index/count, не принимает повтор части и старый seq.
Части можно получить в ином порядке. Для одного seq должны совпадать part count.
После полноты части склеиваются в новый JPEG. Предел — 8 частичных кадров;
при превышении вытесняется старейший, срок части — 150 ms.
Очистка по времени происходит при следующих пакетах, а не отдельным timer.

Session проверяет receiver, не Assembler. При смене Session нужен новый Assembler.
Нельзя объединять части из двух запусков sender только по совпавшему seq.

## Заголовок звука: 23 байта

Python: `struct.Struct('!4sQIIHB')`. Заголовок big-endian,
**полезные сэмплы PCM signed int16 little-endian**, interleaved channels.

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 4 | WA40 |
| 4 | 8 | Session uint64 |
| 12 | 4 | Seq uint32, на каждый пакет |
| 16 | 4 | Sample rate uint32: 16000, 24000, 44100, 48000 |
| 20 | 2 | Frames uint16 |
| 22 | 1 | Channels: 1 или 2 |
| 23 | ≤1200 | PCM16 little-endian |

Полный размер должен быть ровно `23 + Frames*Channels*2`, Frames ≥1.
Один packet вмещает максимум 600 mono frames либо 300 stereo frames.
Если блок не помещается, sender делит его по целым frames, без отдельной сборки
на приёмнике. Номер seq увеличивается для каждого полученного PCM-пакета.

Нормализация: `float32(int16)/32768`. При кодировании положительный предел
`32767/32768`, отрицательный −1. Заголовок и PCM нельзя декодировать одним endian.

## Порядок и перегрузка

Сравнение seq: `a != b && uint32(a-b) < 0x80000000`. Переход `0xffffffff → 0`
корректен, разность ровно в половину диапазона считается неоднозначной/старой.
Видео после завершения нового seq отбрасывает запоздавшие старые кадры.
Audio receiver также отбрасывает старые seq и не переставляет их в jitter buffer.

Доставка UDP обходится без ACK на каждый пакет, повторной передачи и FEC.
Пропавший видеофрагмент делает JPEG неполным. Для звука нехватка данных в playback превращается
в тишину, однако протокол не восстанавливает точную временную позицию каждого
потерянного пакета. Timestamp capture/presentation в заголовках отсутствует.

FIFO audio на 64 пакета не означает фиксированное число миллисекунд: при максимальном
stereo payload и 48 kHz это до 400 ms PCM, а фактический размер блока меняет расчёт.
Пределы rings и политика удаления старого материала дополнительно влияют на latency.

## Обратная связь и адаптация камеры и экрана

Приёмник посылает вместе с периодической подпиской ASCII-сообщение
`<magic> STAT <session_hex16> <expected> <complete>`. Допустимы WC30 и WS40,
`expected` 6…600 и `complete` от 0 до `expected`. Счётчик expected оценивается
по последовательности кадров, complete — по собранным JPEG. В малом окне
приёмник допускает один кадр на границе отчёта. Передатчик принимает STAT
только от действующей подписки с тем же IP:портом и для своей сессии.

В каждом двухсекундном интервале передатчик выбирает худшую свежую оценку среди
подписчиков. Свежесть отчёта ограничена тремя секундами. Если раньше STAT
приходил, SUB продолжается, а новых STAT нет более девяти секунд при хотя бы
шести попытках отправки, контроллер рассматривает это как возможную потерю
downlink. Приёмник, который никогда не посылал STAT, работает по прежнему
протоколу. Без подписчиков контроллер сбрасывается при следующей оценке кадра.

[Контроллер](../go-version/adaptive_video.go) ограничивает FPS до 100, 80, 65,
50 или 35% от настройки. Ухудшение на одну ступень требует двух оценок потерь
от 12% или одной от 35%. Для восстановления одной ступени нужны шесть окон с
потерями от 0 до 3% подряд. Неопределённая оценка сбрасывает счётчики серии.
За ступенью 80% может снижаться качество JPEG. При `adaptive_resolution`
ступени 50% и 35% также ограничивают ширину до 85% и 68% исходного лимита с
нижним порогом 640 px для источников шире 640 px. Для нативного MJPG камеры
пропускаются кадры без перекодирования. Адаптация включена по умолчанию,
динамическая ширина выключена. Звук использует собственный неизменный формат.

Каждый подписчик получает копию того же JPEG. Передатчик выделяет до 45 мс
на отправку кадра одному подписчику, а очередь Latest оставляет свежий кадр.
Число приёмников влияет на исходящий трафик и общую ступень качества.
STAT оценивает завершённость кадров. Он не измеряет пропускную способность,
сквозную задержку или потерю отдельных фрагментов.

## Границы применения

Magic, session и проверка source IP защищают от смешивания потоков, но не от
злоумышленника. Нет аутентификации, шифрования и защиты от поддельных SUB.
Video SUB может направить ответ на объявленный порт того же source IP.
Это реализация для доверенной LAN, её нельзя без переработки выставлять в Интернет.
Для иной сети сначала проектируют аутентификацию, transport security, MTU,
управление перегрузкой и новое версионирование протокола.

Тесты: `TestFragmentCompatibilityAndReordering`, `TestAssemblerBoundsAndExpiry`,
`TestPCMCompatibilityAndClipping`, `TestUDPVideoLoopback` и три interop tests.
